# Case study: Misha Weekly Monitor

This case study describes a recurring research workflow for an independently developed visual novel. It demonstrates how a broad goal — keeping track of promotional opportunities — can be translated into a bounded task with clear filters and a predictable report.

## The problem

Small game teams have limited time for promotion. Relevant opportunities may be announced across showcase pages, festival websites, award programmes, creator channels and publication sites.

Checking all of these sources manually every week is time-consuming. A recurring scan can help surface opportunities for review, provided that it filters aggressively and does not mistake a superficially relevant result for a viable one.

## The task's objective

Find new or materially updated opportunities that could help the game reach players.

The scan covers:

- Indie showcases and festivals.
- Awards and competitions.
- Streamers, reviewers, curators and publications.
- Steam events and promotional opportunities.
- Grants, networking opportunities and relevant calls for submissions.

## Constraints

The monitor uses project-specific filters. Examples include:

- Prefer opportunities where reviewers can access and play the game.
- Exclude awards evaluated only through a video submission.
- Exclude opportunities that depend on maintaining an X or Bluesky presence.
- Prefer free or low-cost opportunities.
- Do not repeat previously reported items without a meaningful update.

These constraints turn a generic search into a more useful shortlist.

## Report format

A practical report can be organised around a small number of prioritised actions:

| Field | Purpose |
|---|---|
| Opportunity | Identify the event, organisation or creator |
| Fit | Explain why it matches the game |
| Requirements | Summarise relevant eligibility conditions |
| Deadline | Show the published submission date, if available |
| Cost | State the fee, if published |
| Source | Link to the official announcement or application page |
| Action | Explain what the team would need to do next |

The report should distinguish verified facts from uncertainty. For example, an opportunity should not be described as free if the fee is simply not listed.

## Why the workflow is useful

The value is not just that information arrives on a schedule. The value comes from combining:

1. A recurring research cadence.
2. A clearly defined scope.
3. Project-specific inclusion and exclusion criteria.
4. A consistent output format.
5. Comparison with previous reports to reduce repetition.

The result is a decision-support workflow, not an autonomous marketing manager. The team still checks the sources, judges the fit and decides whether to apply.

## Lessons from the example

- Start with a real recurring activity rather than inventing a reason to automate.
- Write down constraints before scheduling the task.
- Ask for source links so findings can be checked.
- Track what has already been reported.
- Keep the output short enough that someone will actually read it.
- Revisit the prompt when the project's needs change.

This example is based on a real monitoring workflow for Misha, an independently developed visual novel. Project-specific operational details have been omitted.
